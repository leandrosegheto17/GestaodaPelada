## 1. Plano de execução
**Reaproveitamento:** nada a reaproveitar (sessão manual, sem código). A versão do Postgres deve casar com o `postgres:16` do `db` local (SDD §3, ambiente local) — escolher **16** para não divergir dos testes.
**Camada:** não cria arquivo no repositório. Cria o artefato externo `neon-projeto`; o roteiro e a evidência ficam só em `## 4` deste arquivo (o runbook `backend/DEPLOY.md` é do TP-0137 — não criar aqui).
**Referência visual:** não se aplica.

Roteiro (o Executor dita, o usuário executa no console do Neon e no SQL Editor):
1. Console Neon → New project: nome `gestaodapelada`, plano Free, região **AWS São Paulo (`aws-sa-east-1`)** (fixa por projeto), Postgres 16. O branch padrão chama-se `main` (produção).
2. No `main`, SQL Editor (como o dono padrão, ex. `neondb_owner`): `CREATE EXTENSION IF NOT EXISTS pgcrypto;`.
3. Ainda no `main`, criar os papéis **antes** de criar o branch `teste` (o branch filho herda papéis e extensões do pai):
   - `pelada_app` (aplicação, usado pelo Hyperdrive no TP-0133) — criar pelo console (Roles → New role) para a senha ser gerada pelo Neon;
   - `pelada_backup` (só leitura): `GRANT CONNECT ON DATABASE neondb`, `GRANT USAGE ON SCHEMA public`, `GRANT SELECT ON ALL TABLES/SEQUENCES IN SCHEMA public` e `ALTER DEFAULT PRIVILEGES FOR ROLE <dono das migrações> IN SCHEMA public GRANT SELECT ON TABLES, SEQUENCES TO pelada_backup` (sem o DEFAULT PRIVILEGES o GRANT de hoje não vale para as tabelas que as migrações criarão depois).
4. Criar o branch `teste` a partir do `main`; repetir o `CREATE EXTENSION IF NOT EXISTS pgcrypto` (idempotente) e conferir que os papéis vieram.
5. Copiar, para o gerenciador de senhas do usuário, as strings **diretas** (host sem `-pooler`, `sslmode=require`) de cada branch: dono/migração `main` e `teste`, `pelada_app` `main` e `teste`, `pelada_backup` `main`. Nada disso em arquivo, chat, issue ou `## 4`.
6. Evidência em `## 4`: print/texto da região do projeto e a saída de `SELECT version(); SELECT extname FROM pg_extension;` em cada branch, e `\du`/`SELECT rolname FROM pg_roles WHERE rolname LIKE 'pelada_%'` — sem host completo nem senha.

DECIDIDO (Coordenador): proposta aceita: migração com o papel dono (`neondb_owner`, string `NEON_URL_MIGRACAO_*`) e `ALTER DEFAULT PRIVILEGES FOR ROLE neondb_owner IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pelada_app` (+ `USAGE, SELECT ON SEQUENCES`); sem DDL para o app. Pergunta original: o aceite e o SDD não dizem qual papel roda as migrações (`migrar.ts`, TP-0015/TP-0135) nem como o `pelada_app` recebe DML nas tabelas que as migrações criarem. Proposta: migração com o papel dono (`neondb_owner`, string = `NEON_URL_MIGRACAO_*` do TP-0134) e `ALTER DEFAULT PRIVILEGES FOR ROLE neondb_owner IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pelada_app` (+ `USAGE, SELECT ON SEQUENCES`), sem DDL para o app. Confirmar com o Coordenador antes da sessão.

Não fazer: plano pago, pooler do Neon, IP allowlist/recurso pago, string de conexão versionada.

## 4. Resultado da execução

Tarefa manual conduzida em sessão com o usuário (17/10/2026). Nenhum arquivo do repositório alterado; nenhum segredo registrado aqui.

**Feito**
- Projeto `gestaodapelada` criado no Neon, plano Free, região AWS São Paulo (`aws-sa-east-1`, confirmada pelo usuário em Settings), PostgreSQL 16.15 (um primeiro projeto criado em 18.6 foi descartado e recriado em 16 para casar com o `postgres:16` local).
- Branches: `production` (padrão; o Neon novo não o chama de `main`) e `teste`, criado a partir de `production` depois dos papéis; recriado uma vez após a correção dos papéis.
- `CREATE EXTENSION IF NOT EXISTS pgcrypto` nos dois branches. `SELECT extname FROM pg_extension` → `plpgsql`, `pgcrypto` nos dois; `crypt('x', gen_salt('bf', 12))` devolve hash nos dois (bcrypt do ADR-015 roda).
- Papéis `pelada_app` e `pelada_backup` criados **por SQL** (`LOGIN`, `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`), com `GRANT CONNECT`/`USAGE ON SCHEMA public`; `pelada_backup` com `SELECT` e `pelada_app` com `SELECT, INSERT, UPDATE, DELETE` (+ `USAGE, SELECT` em sequências) por `ALTER DEFAULT PRIVILEGES FOR ROLE neondb_owner IN SCHEMA public`. Decisão do Coordenador seguida: migrações com `neondb_owner`, sem DDL para o app.
- `SELECT rolname FROM pg_roles WHERE rolname LIKE 'pelada_%'` → `pelada_app`, `pelada_backup` nos dois branches.
- Strings de conexão diretas (sem `-pooler`, `sslmode=require`) guardadas no gerenciador de senhas do usuário: `neondb_owner` em `production` e `teste`, `pelada_app` nos dois, `pelada_backup` só em `production`. Confirmado pelo usuário. Senhas dos papéis não rotacionadas (decisão do usuário; ficaram no histórico do SQL Editor do Neon).

**Achado durante a prova (corrigido)**
- Os papéis criados primeiro pelo console do Neon entram em `neon_superuser` (`pg_write_all_data`, `CREATEROLE`, `CREATEDB`): o `pelada_backup` conseguiu `INSERT`. Papéis apagados e recriados por SQL; consulta de `pg_auth_members` para `pelada_%` → 0 linhas; `rolcreaterole`, `rolcreatedb`, `rolbypassrls` todos `f`.

**Prova de privilégio (branch `teste`, tabela `prova_priv` criada pelo dono depois dos GRANT, removida ao final)**
- `pelada_backup`: `SELECT` ok (prova o DEFAULT PRIVILEGES); `INSERT`, `UPDATE`, `DELETE` → `permission denied for table`; `CREATE TABLE` → `permission denied for schema public`.
- `pelada_app`: `SELECT`, `INSERT`, `UPDATE`, `DELETE` ok; `CREATE TABLE` → `permission denied for schema public`; `DROP TABLE` → `must be owner of table`.

**Testes automatizados:** não se aplicam (tarefa manual).

- A conexão do `pelada_app` e do `pelada_backup` no branch `production` não foi exercitada com `psql` (a prova foi no `teste`; os papéis e GRANTs são os mesmos nos dois, conferidos por `pg_roles`).
