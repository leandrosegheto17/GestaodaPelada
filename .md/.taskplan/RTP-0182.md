# RTP-0182 — QUEBRAS.md: registrar que `jogadorDetalhe.inicioPontuacao` (e `pontuacaoInicial`) são recusados pelo app anterior com schema estrito

Reserva: Livre

Reqs: G-20; ADR-009; RNF-13 · Aceite: `backend/contrato/QUEBRAS.md` ganha a linha de `elenco.detalhe.inicioPontuacao` (campo obrigatório de resposta: aditivo para o `checar-compatibilidade`, mas recusado pelo app anterior, que valida `jogadorDetalhe` com `strictObject`) com o efeito, o motivo de ser aceito e a mitigação; mesma nota para `elenco.detalhe.pontuacaoInicial`; `checar-compatibilidade` e `format:check` limpos

## 1. Plano de execução
Achado (QA da TP-0209, severidade Baixa): a resposta de `GET/PATCH/POST …/jogadores/:id` ganhou `inicioPontuacao` (obrigatório). O app em cache valida a resposta com `jogadorDetalhe` estrito (`dados/cliente.ts`, `safeParse`) e recusa o corpo novo, inclusive o do PATCH/POST (a gravação acontece, a tela mostra erro). G-20 pede que a API aceite o PWA anterior por um deploy; para campo de resposta isso só é cumprível sem enviar o campo, então o risco é aceito (mesmo caso de `pontuacaoInicial` na TP-0208, que também ficou sem linha em `QUEBRAS.md`). Atenuantes: front e API saem no mesmo Worker; o service worker só cacheia o ranking público; `FaixaNovaVersao` recarrega com um toque; só a ficha do jogador (admin) é afetada.
1. Em `QUEBRAS.md`, na seção "Retiradas em dois deploys" (ou uma seção "Respostas recusadas pelo app anterior"), registrar `elenco.detalhe.inicioPontuacao` e `elenco.detalhe.pontuacaoInicial`: efeito, motivo e mitigação operacional ("avisar os admins para tocar Recarregar ao ver Nova versão antes de abrir a ficha").
2. Se o Coordenador quiser fechar a classe de risco, decidir à parte se o front passa a ler respostas de elenco sem `strictObject` (vale só a partir da versão seguinte); não faz parte desta RTP.

**Reaproveitamento:** o formato de `QUEBRAS.md` e o leitor `lerQuebras` (`comparar.ts`); nada novo.
