1. TDD: testes do §2 primeiro. Convenção de parâmetros do TP-0014/TP-0016 (executor 1º, `grupoId` logo depois). Datas como string `AAAA-MM-DD` (ADR-012); momentos (`agora`) e autor vêm do chamador (G-06).
2. Tipos: `Jogador { id, apelido, anoNascimento, posicao, telefone|null, periodos: { inicio, fim|null }[] }` (períodos em ordem de início); `posicao` com o enum do `contrato/base` (TP-0005). Erros tipados `ApelidoEmUso`, `PeriodoInvalido`, `JaAtivo`.
3. `listar(db, grupoId)` e `buscar(db, grupoId, jogadorId)` → uma consulta cada, com `json_agg(... ORDER BY inicio)` dos períodos (sem N+1); `buscar` de outro grupo → `null`.
4. `criar(tx: Tx, grupoId, { apelido, anoNascimento, posicao, telefone, dataEntrada, autor, agora })` → id: insere jogador + período `[dataEntrada, ∅)`. Exige `Tx` no tipo (duas tabelas, ADR-014 §3). Índice `lower(apelido)` → `ApelidoEmUso`.
5. `editar(tx, grupoId, jogadorId, { …dados, dataEntrada?, autor, agora })` → boolean: atualiza dados e `alterado_por/em`; `dataEntrada` move o `inicio` do 1º período (menor início); `CHECK fim >= inicio` → `PeriodoInvalido`. A regra "presença antes da nova data → 422" (L-11) é da rota TP-0071 (ver PENDENTE).
6. `inativar(db, grupoId, jogadorId, dataSaida)` → `'ok' | 'sem_periodo_aberto'` (fecha o aberto; `fim < inicio` → `PeriodoInvalido`).
7. `reativar(db, grupoId, jogadorId, dataInicio)` → id do período: `INSERT … SELECT` só se o jogador é do grupo e `dataInicio` > último `fim`; índice parcial de período aberto → `JaAtivo` (RN-06, ADR-006 §5: sem sobreposição).
8. `excluir(tx, grupoId, jogadorId)` → boolean: apaga períodos e jogador; FK de presença/nota (23503) → erro `JogadorComHistorico` (barreira contra corrida com `temHistorico`). Auditoria é da rota TP-0074.
9. `temHistorico(db, grupoId, jogadorId)` → `EXISTS` em `presencas` OR `notas` numa consulta (registro financeiro entra no I4, L-10).
10. Não fazer: validação de limites (contrato), ativos numa data (`aplicacao/elenco/ativos`, TP-0052), auditoria.

## 2. Plano de teste
`backend/api/test/repositorios/jogadores.test.ts` (pool de Workers + Postgres), grupos A e B de fábrica, datas derivadas de `relogioFixo` (sem literal), tudo apagado no `afterEach` mesmo em falha (CONVENCOES §7):
- criar → `buscar` traz 1 período aberto desde a data de entrada; apelido `"Toninho"` e `"TONINHO"` no mesmo grupo → `ApelidoEmUso`; mesmo apelido no grupo B → aceito.
- editar: dados e `alterado_em`; nova data de entrada move só o 1º período; nova data depois do `fim` do 1º → `PeriodoInvalido`.
- inativar fecha o aberto; inativar de novo → `sem_periodo_aberto`; reativar abre novo e mantém o anterior; reativar ativo → `JaAtivo`; reativar com data ≤ último fim → recusado.
- `temHistorico`: falso sem nada; verdadeiro com uma presença (via `sql.ts`) e com uma nota; `excluir` sem histórico apaga jogador e períodos; com presença → `JogadorComHistorico`.
- isolamento: `buscar`/`editar`/`inativar`/`reativar`/`excluir`/`temHistorico` com id de B pelo grupo A → null/false e B intacto.
- sem N+1: `listar` com 3 jogadores e 2 períodos cada = 1 consulta (espião no executor); `criar` sem `Tx` não compila (`@ts-expect-error`).
Comando: `pnpm --filter @pelada/api test -- jogadores grupos` + `node backend/scripts/checagens/checar-grupo-id.mjs`.
