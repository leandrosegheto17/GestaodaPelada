Evidência: lista de secrets sem valores

## 1. Plano de execução
**Reaproveitamento:** USAR os valores do gerenciador de senhas gerados no TP-0132 (strings diretas do dono/migração de `main` e `teste`, `pelada_backup` de `main`) e no TP-0133 (token e Account ID da Cloudflare). Nada de código.
**Camada:** nenhum arquivo do repositório. Artefato externo `github-secrets`, consumido por TP-0135 (`deploy.yml`) e TP-0136 (`backup.yml`).
**Referência visual:** não se aplica.

Roteiro (`gh` autenticado no repositório `leandrosegheto17/GestaodaPelada`):
1. Environments: `producao` com *required reviewers* = o usuário e *deployment branches* = só `main`; `teste` sem aprovação. (`gh api -X PUT repos/{owner}/{repo}/environments/producao` com `reviewers` e `deployment_branch_policy`, ou pelo Settings.)
2. Gerar a `BACKUP_CHAVE`: `openssl rand -base64 48` (serve como frase do `openssl enc -aes-256-cbc -pbkdf2` ou do `gpg --symmetric`, qualquer que seja a escolha do TP-0136); salvar primeiro no gerenciador de senhas, depois no GitHub. Sem a cópia fora do GitHub o backup é irrecuperável.
3. Neon: criar API key com escopo do projeto (Project-scoped, se o plano permitir; senão pessoal) e anotar o Project ID (L-8).
4. Gravar cada secret lendo da entrada padrão, sem valor na linha de comando: `gh secret set NOME [--env <ambiente>]` e colar quando pedido. Escopo proposto (ver PENDENTE): `NEON_URL_MIGRACAO_PROD` no environment `producao`; `NEON_URL_MIGRACAO_TESTE` no `teste`; `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `NEON_API_KEY`, `NEON_PROJECT_ID` no repositório (os dois deploys usam); `NEON_URL_BACKUP_LEITURA` e `BACKUP_CHAVE` no repositório (o cron do backup não pode esperar aprovação manual).
5. Evidência em `## 4`: saída de `gh secret list` e `gh secret list --env producao`/`--env teste` (só nomes e datas) e `gh api repos/{owner}/{repo}/environments --jq '.environments[] | {name, protection_rules}'`.

PENDENTE: o ADR-011 e o SDD §3 assumem **repositório privado**, mas o `leandrosegheto17/GestaodaPelada` está **público** hoje. No GitHub Free, environment secrets e required reviewers só existem em repositório público; se o repositório for tornado privado, o `producao` com aprovação manual (G-15) deixa de ser possível sem plano pago (G-13). E, público, os artefatos do backup cifrado (TP-0136) ficam baixáveis por qualquer conta do GitHub. Decisão do usuário/Coordenador antes da sessão: manter público (aprovação manual funciona; backup cifrado exposto a download) ou privado (sem aprovação manual nem environment secrets no Free → revisar G-15/ADR-011).
DECIDIDO (Coordenador): escopo do passo 4 confirmado (NEON_URL_MIGRACAO_PROD no environment `producao`, NEON_URL_MIGRACAO_TESTE no `teste`; demais secrets no repositório). Obs.: o ambiente `producao` com aprovação depende da decisão de visibilidade do repositório (PENDENTE acima, do usuário). Pergunta original: o aceite não fixa o escopo (repositório × environment) de cada secret; confirmar a proposta do passo 4, que o TP-0135 e o TP-0136 vão referenciar.
