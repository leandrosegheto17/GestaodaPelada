Reserva: Livre
ID no TASK.md: TP-0074 · Lote: L16 · Agente: executor · Chapéu: Backend · Est: 0,5 d · Dep: TP-0023, TP-0032, TP-0046, TP-0030, TP-0033 · Status no TASK.md: Pendente

## 1. Plano de execução
**Reaproveitamento:** USAR `ErroJogadorComHistorico` (`codigo: jogador_com_historico`, `sugestao: 'inativar'`) de `backend/contrato/src/elenco.ts` (TP-0023); `exigirVinculo`/`c.var.sessao` (TP-0032/TP-0031); `jogadores.buscar`, `jogadores.temHistorico`, `jogadores.excluir(tx, grupoId, jogadorId)` e o erro `JogadorComHistorico` (FK) de `backend/api/src/infraestrutura/db/repositorios/jogadores.ts` (TP-0046); `auditoria.registrar(tx, grupoId, { autor, acao, entidade, entidadeId, resumo, agora })` de `repositorios/auditoria.ts` (TP-0030); `emTransacao` (TP-0014); relógio e erros de `src/entrada/erros.ts` (TP-0013); `test/isolamento/casos.ts` (TP-0033). O TP-0189 só acrescenta o financeiro dentro de `temHistorico`; não criar outra checagem aqui.
**Camada:** `backend/api/src/aplicacao/elenco/excluir.ts` (jogador + períodos + auditoria numa transação, ADR-014 §3) → `aplicacao`; `backend/api/src/entrada/rotas/grupo/jogador-excluir.ts` → `entrada`; registro em `src/entrada/app.ts` depois dos middlewares de grupo (ler logo antes; TP-0072/TP-0073 editam em paralelo).
**Referência visual:** não se aplica.

1. TDD (Seção 2) primeiro.
2. Rota: `:id` uuid antes do banco → 404 sem consulta; sem corpo; sucesso → 204 (interpretação registrada no TP-0023).
3. `excluirJogador(db, grupoId, jogadorId, { autorContaId, agora })` dentro de `emTransacao`: `buscar` (null → 404); `temHistorico` → `ComHistorico(apelido)`; senão `excluir(tx, …)` + `auditoria.registrar(tx, grupoId, { autor: { tipo: 'conta', contaId }, acao: 'jogador_excluido', entidade: 'jogador', entidadeId, resumo: { apelido }, agora })`. `JogadorComHistorico` vindo da FK (presença gravada entre a checagem e o DELETE) → o mesmo 409, transação desfeita.
4. 409: `{ erro: { codigo: 'jogador_com_historico', mensagem: '<apelido> tem histórico de partidas e não pode ser excluído.', sugestao: 'inativar' } }`, validado pelo schema do contrato antes de responder.
5. `casos.ts`: `DELETE /api/grupos/:grupoId/jogadores/:id` → `tipo: 'grupo'`.
Não fazer: apagar presença/nota (a recusa é a regra, RF-22); anonimização (SDD §7, Fase 2); checar financeiro (TP-0189).

## 2. Plano de teste
`backend/api/test/aplicacao/elenco/excluir.test.ts` e `backend/api/test/rotas/grupo/jogador-excluir.test.ts` (pool de Workers + Postgres; fábricas de grupo/admin/jogador; presença e nota via `test/apoio/sql.ts`; tudo, inclusive a linha de auditoria, apagado no `afterEach`; instante de `relogioFixo`; `X-Pelada: 1`):
- sem histórico → 204; `buscar` = null; períodos apagados; 1 linha de auditoria (`jogador_excluido`, autor = conta do admin, `resumo` só com `apelido`, sem telefone).
- com uma presença → 409 com corpo igual à forma de `erro-jogador-com-historico.json` (passa em `ErroJogadorComHistorico`); jogador e períodos intactos; sem auditoria. Com só uma nota → 409 igual.
- corrida: dublê de `temHistorico` devolvendo falso com presença gravada → FK → 409 e nada apagado.
- atomicidade: dublê de `auditoria.registrar` que lança → jogador não é apagado (500 genérico).
- 404 para id de outro grupo (jogador de B continua), inexistente e malformado (sem consulta); excluir duas vezes → 2ª 404; 401 sem sessão; 403 sem `X-Pelada`; `Cache-Control: no-store`; isolamento verde.
Comando: `pnpm --filter @pelada/api test -- jogador-excluir excluir isolamento`.

## 3. Plano de validação de segurança
- ADR-005/G-03: `grupoId` em todas as chamadas; id alheio = 404 idêntico, dado de B intacto (conferir no diff que nenhum DELETE sai sem `grupo_id`).
- RNF-12/G: auditoria na mesma transação, só acrescenta; `resumo` sem telefone, ano ou qualquer dado além do apelido (G-08; a lista negada do TP-0030 cobre).
- LGPD (SDD §7): exclusão só sem histórico; com histórico a saída é inativar — nada de remoção parcial.
- G-09 `X-Pelada: 1`; CONVENCOES §8 uuid antes do banco; mensagem do 409 traz só o apelido.
