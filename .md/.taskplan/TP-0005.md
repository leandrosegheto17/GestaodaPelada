# TP-0005 — Contrato base: erro padrão, enums, limites e tipos primitivos

Reserva: Livre
ID no TASK.md: TP-0005 · Lote: L01 · Agente: executor · Chapéu: Backend · Est: 1 d · Dep: TP-0001 · Status no TASK.md: Pendente
Reqs: SDD §2 (C6); CONVENCOES §8; Seção 1.4 · Aceite: Em `backend/contrato/src`: schema de erro no formato de `respostas/erro-*.json`; enums (situação da presença, posição, frequência, dia da semana, situação comercial, tipo de lançamento, formato do simulador, escopo da sessão); `limites.ts` com a tabela da Seção 1.4; tipos data, mês, horário, uuid, slug, centavos inteiros. Testes de borda por limite (mínimo, máximo, um a mais, estouro, malformado). Sem lógica de negócio

## 1. Plano de execução
**Reaproveitamento:** USAR o pacote `backend/contrato` de TP-0001 (`monorepo`: `package.json` com `zod`, `tsconfig`, `src/index.ts`). Nada a extrair.
**Camada:** `@pelada/contrato` (`backend/contrato/src`), só schemas, enums e constantes (SDD §2; G-01: sem lógica de negócio).
**Referência visual:** não se aplica.

1. `src/limites.ts`: objeto `as const` com a tabela da Seção 1.4 (apelido 2–30, nome do grupo 3–60, habilidade 2–30, nome do admin 2–60, e-mail ≤ 254, senha 8–72 caracteres e ≤ 72 bytes, ano de nascimento mínimo 1940 e idade mínima 10, pesos −10..10, N 2–11, K 0–20, aptos ≤ 60, nota 1–10, descrição 1–80, valor 1..99.999.999, saldo inicial −99.999.999..99.999.999, slug 1–64, corpo 16 KB / 1 KB público). Só números; quem monta o schema de cada campo é o contexto.
2. `src/primitivos.ts`: `data` (`AAAA-MM-DD` com dígitos ASCII e data de calendário real: 29/02 só em bissexto), `mes` (`AAAA-MM`, mês 01–12), `horario` (`HH:MM` 00:00–23:59), `uuid`, `slug` (`^[a-z0-9-]{1,64}$`), `centavos(min, max)` (inteiro seguro na faixa; recusa float, NaN, ±Infinity, string). "Partida ≤ hoje" e ano máximo dependem de `hoje` e ficam nos contextos (TP-0023/0024).
3. `src/enums.ts` (tuplas `as const` + `z.enum` + tipo): situação da presença `ausente|presente|lesionado|expulso` (RN-02; o "falta"/"fora" da rodada do ranking é do `contrato/publico`, TP-0020); posição `goleiro|defensor|meio_campo|atacante`; frequência `semanal|quinzenal|mensal`; dia da semana `domingo|segunda|terca|quarta|quinta|sexta|sabado`; situação comercial `uso_proprio|trial|ativo|inadimplente|cancelado` (RF-04); tipo de lançamento `entrada|saida`; formato `dois_times|varios_times`; escopo `completo|troca_de_senha`. Valores conferidos contra `respostas/*.json`.
4. `src/erro.ts`: `{ erro: { codigo: string snake_case, mensagem: string, campos?: Record<string,string> } }` e uma função `estenderErro(extra)` para os contextos acrescentarem campos (`dataExistente`, `liberaEm`, `sugestao`) sem repetir a base; constantes dos códigos comuns (`validacao`, `nao_encontrado`, `nao_autenticado`, `erro_interno`).
5. `src/index.ts` reexporta. Cada arquivo ≤ 300 linhas.

DECIDIDO (Coordenador): uuid só para id de ENTRADA (rota/corpo; malformado → 404 sem consulta); id de RESPOSTA = `idResposta` (string não vazia, exportado do `contrato/base`). Os arquivos do mockup não mudam. Vale para TP-0019 a TP-0024, TP-0145, TP-0146, TP-0159. Pergunta original: a Seção 1.4 diz "ids: uuid", mas todos os ids em `.md/mockup/respostas/` são legíveis (`g-quinta`, `j-alemao`, `c-carlos`, `h-passe`), e o [CT] exige que todo arquivo de `respostas/` passe no schema. Proposta: `uuid` só para id **de entrada** (parâmetro de rota/corpo, malformado → 404 sem consulta) e id **de resposta** como `idResposta` = string não vazia; ou trocar os ids do mockup por uuids. Decisão do Coordenador antes de TP-0019+.

## 2. Plano de teste
