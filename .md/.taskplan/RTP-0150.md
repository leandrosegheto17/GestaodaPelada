# RTP-0150 — deploy.yml: enviar o token da Cloudflare ao curl sem poder injetar diretivas

Reserva: Livre
ID no TASK.md: RTP-0150 · Lote: Refatoração Lote-30 · Agente: executor · Chapéu: Backend · Est: 0,1 d · Dep: RTP-0143 · Status no TASK.md: Pendente
Reqs: G-21; DevSecOps da RTP-0143 (S1) · Aceite: o token chega ao `curl` sem que aspas, barra invertida ou quebra de linha possam injetar diretivas da config do curl (validar `^[A-Za-z0-9_-]+$` antes de usar, falhando fechado sem eco do valor, ou usar `curl -H @-` com o cabeçalho por stdin); teste com token `x"\noutput = "f"` não cria arquivo nem faz segunda requisição e sai rc 1; `actionlint` em 0

## 1. Plano de execução
Achado (baixa, DevSecOps da RTP-0143, S1): o passo monta a config do curl com `printf 'header = "Authorization: Bearer %s"\n' "$CLOUDFLARE_API_TOKEN" | curl --config -`. Um token com `"`, `\` ou `\n` injeta diretivas (provado com servidor local: `\n` no token fez o curl criar um arquivo via `output` e fazer uma segunda requisição via `url`). O risco real é só de quem controla o secret, e o environment `producao` exige aprovação manual, mas é correção de poucas linhas. Fazer junto da RTP-0148, que mexe no mesmo passo do `deploy.yml`.
**Reaproveitamento:** o passo existente do `deploy.yml` (RTP-0143).

## 2. Plano de teste
Teste que reproduz o passo com servidor local e o token hostil (`x"\noutput = "f"`): sem a correção cria arquivo/2ª requisição; com a correção sai rc 1 e nada acontece. `actionlint` (docker).

## 3. Plano de validação de segurança
G-21: token fora de argv, sem eco, sem injeção de diretiva; mensagem de erro sem o valor.
