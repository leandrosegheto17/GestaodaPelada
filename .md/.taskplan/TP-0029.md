# TP-0029 — Repositórios de grupos e de vínculos

Reserva: Livre
ID no TASK.md: TP-0029 · Lote: L06 · Agente: executor · Chapéu: Backend · Est: 1 d · Dep: TP-0014, TP-0016, TP-0017, TP-0026 · Status no TASK.md: Pendente
Reqs: ADR-005; ADR-016; RF-02 a RF-10, RF-13, RF-15, RF-18 · Aceite: [RP] Grupos: por id, por slug (inclui arquivado), slugs existentes, criar, atualizar dados, situação, arquivar e reativar. Vínculos: (conta, grupo), grupos da conta, admins do grupo, criar, remover, contar admins, alterar acessa_financeiro

## 1. Plano de execução
**Reaproveitamento:** USAR `ExecutorDb`/`Tx` e o desembrulho interno de `infraestrutura/db/` (TP-0014); tabelas `grupos`/`vinculos_admin`/`contas` tipadas em `tipos.ts` (TP-0025, TP-0026); `criarFabrica`, `relogioFixo` (TP-0017) e `test/apoio/sql.ts` (TP-0025). Tipos de enum (dia, frequência, situação comercial) e de data/horário de `@pelada/contrato` base (TP-0005). Contas de teste: fábrica `test/apoio/fabricas/contas.ts` do TP-0027 se já existir; senão via `test/apoio/sql.ts`, trocando para a fábrica antes de entregar (nunca uma segunda fábrica de contas). O instante vem do chamador (`agora`, relógio da API, G-06).
**Camada:** `backend/api/src/infraestrutura/db/repositorios/{grupos.ts,vinculos.ts}` (módulo de dados); fábricas `backend/api/test/apoio/fabricas/{grupos.ts,vinculos.ts}`.
**Referência visual:** não se aplica.

1. Convenção de parâmetros: a do TP-0014/TP-0016 (executor 1º, `grupoId` logo depois). Funções sem grupo (público, criação e dono) entram **por função** em `backend/scripts/checagens/grupo-id-excecoes.json` com motivo: `buscarPorSlug`, `slugsComBase`, `criar`, `gruposDaConta`.
2. Datas e horário saem como string (ADR-012): `to_char(horario,'HH24:MI')`, `to_char(trial_inicio,'YYYY-MM-DD')` no SELECT — nunca `Date` do `pg`. Um mapeador de linha único (`paraGrupo`) usado por todas as leituras do arquivo.
3. `grupos.ts`:
   - `buscarPorId(db, grupoId)` e `buscarPorSlug(db, slug)` → `Grupo | null` (com `arquivadoEm`; quem decide 404/"indisponível" é a rota/middleware).
   - `slugsComBase(db, base)` → `string[]` (`slug = $1 OR slug LIKE $1 || '-%'`, inclui arquivados) — entrega ao `dominio/slug` só o conjunto que pode colidir, sem varrer a tabela.
   - `criar(db, { nome, slug, diaSemana, frequencia, horario, criadoPor, agora })` → id; violação do índice único do slug → erro tipado `SlugEmUso` (a nova tentativa com sufixo é do caso de uso, ADR-016 §2).
   - `atualizarDados(db, grupoId, { nome, diaSemana, frequencia, horario })` (o tipo não tem `slug`); `alterarSituacao(db, grupoId, { situacao, trialInicio })`; `arquivar(db, grupoId, agora)`; `reativar(db, grupoId)` → `boolean` (false se não existe). Nenhuma função de DELETE (slug nunca reutilizado).
4. `vinculos.ts`:
   - `buscar(db, grupoId, contaId)` → `{ acessaFinanceiro, grupoArquivado } | null` numa consulta (join com grupos) — é o que o middleware do TP-0032 consulta por requisição.
   - `gruposDaConta(db, contaId)` → `[{ grupoId, nome, slug, acessaFinanceiro }]` só de grupos não arquivados, por nome (TP-0035).
   - `adminsDoGrupo(db, grupoId)` → `[{ contaId, nome, email, acessaFinanceiro }]` por nome (join contas; sem hash).
   - `criar(db, grupoId, { contaId, acessaFinanceiro, criadoPor, agora })`; duplicado → erro tipado `VinculoDuplicado`. `remover(db, grupoId, contaId)` → boolean. `alterarAcessaFinanceiro(db, grupoId, contaId, valor)` → boolean.
   - `contarAdmins(db, grupoId)`: quando recebe `Tx`, trava a linha do grupo (`SELECT … FOR UPDATE`) antes de contar, para duas remoções simultâneas não zerarem os admins (RN-13; uso no TP-0065).

PENDENTE: o painel do dono (TP-0054, que só usa `repo/grupos` e `repo/vinculos`) precisa de **todos os grupos com metadados e nomes dos admins** (`dono-painel.json`), e o aceite não lista essa leitura. Incluir aqui `listarTodosComAdmins(db)` (uma consulta com `array_agg`, exceção do dono no `grupo-id-excecoes.json`) ou deixar para o TP-0054 acrescentar?

## 2. Plano de teste
`backend/api/test/repositorios/{grupos,vinculos}.test.ts` (pool de Workers + Postgres), dois grupos A e B de fábrica, apagados em `afterEach` mesmo em falha; momentos de `relogioFixo`:
- isolamento: `buscarPorId`, `atualizarDados`, `alterarSituacao`, `arquivar`, `buscar`/`remover`/`alterarAcessaFinanceiro` com o id de B mas conta de A (ou id inexistente) → null/false e B intacto.
- `buscarPorSlug` acha arquivado; `slugsComBase('pelada')` traz `pelada`, `pelada-2`, não traz `peladao`; `criar` com slug repetido → `SlugEmUso`.
- `atualizarDados` muda nome e mantém slug; horário volta `'20:00'`, `trialInicio` volta `'AAAA-MM-DD'` (string); situação `trial` com data e volta para `ativo` com `null`.
- arquivar → `gruposDaConta` deixa de listar e `buscar` traz `grupoArquivado: true`; reativar restaura.
- vínculo duplicado → `VinculoDuplicado`; `adminsDoGrupo` sem `senhaHash`; `contarAdmins` com 2 e após remover 1.
- sem N+1: `gruposDaConta` e `adminsDoGrupo` com 3 linhas fazem 1 consulta (espião no executor).
Comando: `pnpm --filter @pelada/api test -- grupos vinculos` + `node backend/scripts/checagens/checar-grupo-id.mjs`.

## 3. Plano de validação de segurança
- ADR-005/G-03: toda função de dado de grupo filtra por `grupoId`; id de outro grupo = "não encontrado"; exceções do `grupo-id-excecoes.json` só as 4 listadas, com motivo.
- ADR-016: nenhuma escrita de slug fora de `criar`; o gatilho do TP-0026 continua sendo a última barreira.
- RN-13: contagem com trava dentro da transação (corrida de remoção).
- Nenhuma leitura devolve `senha_hash` nem `e_dono` de contas; consultas parametrizadas (nada de `sql.raw` com entrada).
