## Bloqueio 001 — 2026-10-17 (BK-0001)
- Reportado por: Executor
- Escalado para: Coordenador
- Artefato/trecho afetado: TP-0017
- Descrição: Projeto workers do Vitest (vitest-pool-workers 0.23.0 / workerd 1.20260815.1) recusa compatibility_date 2026-10-01 do wrangler.jsonc; com a data forçada o pg quebra (import fora de módulo). Decidir: atualizar pool/miniflare para workerd >= 1.20261012 (muda dependência e lockfile) ou reduzir compatibility_date.
- Impacto se não resolvido: apoio-banco.test.ts e testes de rota da API no pool workers não rodam; job api do CI provavelmente falha
- Sugestão: avaliar atualização do pool; senão reduzir a data e registrar em ADR
- Status: Em aberto

## Resolução
Decisão (coordenador, 2026-10-17): opção 2, reduzir `compatibility_date` para `2026-08-15` (ADR-018).
Motivo: o npm tem como última versão do pool a 0.23.0 (workerd 1.20260815.1), então a atualização (opção 1) não existe; a data 2026-10-01 não é exigida por nenhum ADR/SDD/GUARDRAILS (ADR-014 exige só `nodejs_compat` + Hyperdrive); a mudança não mexe em dependência nem lockfile.
Ação (Executor, dentro de TP-0017): em `wrangler.jsonc` linha 5 trocar `"compatibility_date": "2026-10-01"` por `"2026-08-15"` (env.teste herda); manter `nodejs_compat`; não mexer em `pnpm-lock.yaml`. Aceite: `pnpm --filter @pelada/api test` roda o projeto `workers` (apoio-banco.test.ts e testes de rota) sem erro de data nem falha do `pg`, e `wrangler.test.ts` continua verde. Se o `pg` ainda quebrar com a data aceita, é outro defeito: abrir novo BK com o erro exato.
Bloqueio pode ser fechado após o Executor aplicar e confirmar o teste; TP-0017 volta à fila.
