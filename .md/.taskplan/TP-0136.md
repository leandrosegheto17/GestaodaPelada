# TP-0136 — Workflow de backup diário (`backup.yml`)

Reserva: Livre
ID no TASK.md: TP-0136 · Lote: L30 · Agente: executor · Chapéu: Backend · Est: 0,75 d · Dep: TP-0134 · Status no TASK.md: Pendente
Reqs: ADR-011; RNF-07; SDD §6 T-08 · Aceite: Cron às 07:00 UTC (04:00 de São Paulo) + manual; `pg_dump` com o usuário só de leitura; cifra simétrica (age ou openssl AES-256) com BACKUP_CHAVE; artefato com retenção de 30 dias; falha notifica pelo GitHub. Evidência: execução manual verde e artefato baixável

## 1. Plano de execução
**Reaproveitamento:** secrets `NEON_URL_BACKUP_LEITURA` e `BACKUP_CHAVE` do TP-0134. Esta tarefa CRIA a action composta `.github/actions/dump-cifrado/action.yml`, que o `deploy.yml` (TP-0135) usa para o dump pré-migração — um só lugar para dump + cifra + upload (CONVENCOES regra 1). Nada mais a reaproveitar (não precisa de pnpm/node).
**Camada:** `.github/workflows/backup.yml` e `.github/actions/dump-cifrado/` (item de topo `.github/`, SDD §2); script de shell `.github/actions/dump-cifrado/dump-cifrado.sh` (lógica fora do YAML para passar no `shellcheck -x`).
**Referência visual:** não se aplica.

1. `dump-cifrado.sh` (`set -euo pipefail`, sem `set -x`), entradas por variável de ambiente `PG_URL`, `CHAVE_AGE`, `SAIDA`:
   - descobre a versão maior do servidor (`psql "$PG_URL" -Atc 'show server_version_num'` dentro de `docker run --rm postgres:<n>`, ou imagem `postgres:17` para a consulta) e roda `pg_dump --format=custom --no-owner --no-privileges` na imagem `postgres:<versão maior>` (o cliente do runner pode ser mais antigo que o Neon 17);
   - cifra em fluxo, sem arquivo em claro no disco: `pg_dump … | age -r "$(printf '%s' "$CHAVE_AGE" | age-keygen -y)" -o "$SAIDA"` (age é autenticado; instalado por `apt-get install -y age`);
   - falha se o arquivo cifrado tiver 0 byte; imprime só o tamanho e o SHA-256 do arquivo cifrado.
2. `action.yml` (composite): inputs `url`, `chave`, `nome-artefato`, `retencao` (padrão 30); instala `age`, roda o script com os inputs em `env:`, `actions/upload-artifact` com `retention-days`, `if-no-files-found: error`.
3. `backup.yml`: `on: schedule: cron '0 7 * * *'` + `workflow_dispatch`; `permissions: contents: read`; `concurrency: backup` sem cancelar; job único `ubuntu-24.04` → checkout → `uses: ./.github/actions/dump-cifrado` com `NEON_URL_BACKUP_LEITURA`, `BACKUP_CHAVE`, artefato `backup-<AAAA-MM-DD do run em America/Sao_Paulo via TZ=America/Sao_Paulo date>-<run_id>`.
4. Notificação de falha: padrão do GitHub (e-mail ao autor do workflow agendado); registrar em `backend/README.md` (seção "Backup") que a notificação de Actions precisa estar ligada nas configurações do Leandro e apontar o `DEPLOY.md` (TP-0137) para decifrar/restaurar.
5. Evidência: disparo manual verde, artefato baixado e decifrado com a chave do gerenciador de senhas, `pg_restore --list` lista as tabelas (URL do run e saída resumida em `## 4`; disparo só com permissão do usuário).

DECIDIDO (usuário, BK-0010, 2026-10-17): manter `age` (autenticado; repositório público). O `BACKUP_CHAVE` precisa ser uma identidade age (`AGE-SECRET-KEY-1…`, gerada com `age-keygen`). O secret gravado pelo TP-0134 é uma frase-senha (`openssl rand -base64 48`) e não serve: antes do primeiro disparo o usuário gera a identidade, guarda no gerenciador de senhas e regrava com `gh secret set BACKUP_CHAVE` (ainda não há dump cifrado, nada se perde). Não trocar para openssl.
Não fazer: dump de outro branch aqui (o backup diário é o de produção; não há `teste`, ADR-020); guardar o dump em claro; usar `NEON_URL_MIGRACAO_*` (só o usuário de leitura).
