# TP-0008 — `dominio/pontuacao`: pontos de uma presença e acumulado

Reserva: Livre
ID no TASK.md: TP-0008 · Lote: L02 · Agente: executor · Chapéu: Backend · Est: 0,5 d · Dep: TP-0007 · Status no TASK.md: Pendente
Reqs: RN-01, RN-02, RN-04, RN-18 · Aceite: [PD] Pontos = peso da situação combinada com chuva na configuração vigente na data (última com `vigenteDesde` ≤ data); expulso com peso único; ausente sem pontos; acumulado até uma data. Testes com os pesos padrão e com troca de pesos no meio do histórico (partidas anteriores não mudam)

## 1. Plano de execução
**Reaproveitamento:** USAR `compararDatas` de `backend/dominio/src/datas/datas.ts` (TP-0007) para vigência e corte do acumulado; não comparar datas por conta própria. Os pesos padrão da RN-18 viram constante exportada aqui (`PESOS_PADRAO`), que o caso de uso de criação de grupo reutilizará (não repetir os números em outro lugar).
**Camada:** `@pelada/dominio` (`backend/dominio/src/pontuacao/`), regra pura (SDD §2).
**Referência visual:** não se aplica.

1. Tipos em `pontuacao/tipos.ts`: `SituacaoPresenca = 'presente' | 'lesionado' | 'expulso'` (ausência não tem linha, ADR-006 §4); `Pesos` com os 5 campos da forma de `.md/mockup/respostas/pesos.json` (`presencaSemChuva`, `presencaComChuva`, `lesionadoSemChuva`, `lesionadoComChuva`, `expulso`); `ConfigPesos = Pesos & { vigenteDesde: Data; registradoEm: string }`.
2. `pontuacao/pesos.ts`: `PESOS_PADRAO` (1,1,1,1,−1, RN-18); `configVigente(configs, data)` = maior `vigenteDesde` ≤ data; empate no mesmo dia → maior `registradoEm` (ADR-006 §3). Independente da ordem do array.
3. `pontuacao/pontos.ts`: `pontosDaPresenca(situacao, choveu, pesos)` (expulso ignora `choveu`, RN-01); `pontosNaData(situacao, choveu, data, configs)`; `acumuladoAte(presencas, configs, referencia)` = soma das presenças com data ≤ referência (inclusive, RN-01 "até a data de referência"). Entrada: lista `{ data, choveu, situacao }` de um jogador. Ausente/falta não entra (vale 0, RN-03).
4. Para o ranking (TP-0010) não precisar recalcular a vigência por presença em laço quadrático: ordenar as configs uma vez e resolver por busca, função exportada `criarResolvedorDePesos(configs)` que `pontosNaData` usa.
5. Export pelo ponto de entrada do pacote (reler `index.ts` antes; editar só a linha nova).

PENDENTE: partida com data **anterior** à primeira configuração de pesos do grupo (ex.: grupo criado em 05/02 com pesos padrão e partida lançada com data 20/01) — usar a configuração mais antiga ou erro de domínio? Enquanto não decidido, o executor não deve escolher; a sugestão é "usar a mais antiga" (o grupo sempre nasce com uma, RN-18).

Não fazer: ler pesos do banco, validar faixa −10..10 (é do contrato), aplicar a regra "expulso prevalece" (RN-02 é da validação de presenças, TP-0080; aqui cada presença já tem uma situação só).

## 2. Plano de teste
`backend/dominio/src/pontuacao/*.test.ts`, tabelas em inteiros ([PD]):
- Pesos padrão: presente sem/com chuva = 1, lesionado sem/com = 1, expulso com e sem chuva = −1.
- Pesos de `pesos.json` (presença com chuva = 2 a partir de 2026-09-01): partida 2026-08-27 com chuva = 1 (config antiga), 2026-09-01 (dia da troca) = 2, 2026-10-08 = 2.
- Duas configs no mesmo `vigenteDesde`: vale a de `registradoEm` maior; array em ordem invertida dá o mesmo resultado.
- `acumuladoAte`: referência antes da 1ª partida = 0; referência no dia de uma partida a inclui; troca de pesos no meio do histórico não muda o acumulado das partidas anteriores (soma antes/depois da troca conferida à mão).
- Lista vazia = 0; acumulado negativo possível (só expulsões).
- Comando: `pnpm --filter @pelada/dominio exec vitest run src/pontuacao`; checagens da Seção 1.6 disponíveis.

## 3. Plano de validação de segurança
Função pura, sem I/O. Verificar no diff: sem relógio (G-06), sem import externo (G-01), sem ID de tarefa (G-23); só inteiros (nenhuma divisão/float); custo O(n log m) sem laço aninhado sobre presenças × configs (orçamento de 10 ms, G-12/ADR-014).
