## 3. Plano de validação de segurança
- **LGPD / RNF-06:** `pontuacao_inicial` só nas rotas de admin (criar, editar, detalhe) com o mesmo guard de grupo e papel do cadastro de jogador; sem endpoint público que a devolva isolada; telefone nunca lido pelo script; do nascimento só o ano; nenhum log (script, API ou auditoria) com telefone, nascimento, apelido ou nome; o relatório com apelidos existe só no terminal do operador.
- **G-21:** nenhuma credencial, `DATABASE_URL`, caminho de arquivo real, dado real ou fixture com dado real em código, teste, doc, log ou artefato de CI; a conexão do script vem só do ambiente do operador; nenhum agente roda o script contra produção.
- **Transação e integridade (RNF-07):** transação única com rollback total comprovado por teste de falha injetada; backup/ponto de restauração confirmado pelo operador antes da execução real; recusa sem a confirmação.
- **Idempotência:** segunda execução, grupo com partida ou com apelido do arquivo → recusa sem gravar; sem `ON CONFLICT DO UPDATE` silencioso.
- **Isolamento (ADR-005):** toda gravação do script recebe o `grupoId` do grupo alvo; `checar-grupo-id` verde; nenhum acesso a outro grupo.
- **Permissões:** editar a pontuação inicial exige admin do grupo (como RF-20); admin de outro grupo → 404; sessão sem escopo completo → recusada; auditoria com valor anterior (RNF-12) e autor.
- **Exceção RN-24:** a vigência no passado existe só no script; a rota `POST /api/grupos/:g/pesos` continua recusando data no passado (teste mantido).
- **Entrada hostil:** arquivo com linha inválida, fórmulas de planilha, nomes enormes ou caracteres de controle → recusa com o número da linha; SQL sempre parametrizado (Kysely), sem concatenação.
- **Migração:** aditiva, sem apagar dado; revisão do `UPDATE` de posições (sem perda); rollback = `wrangler rollback` + restaurar o branch (SDD §6).

### Riscos e dúvidas (decisão do Coordenador/usuário)
1. **Dados reais não casam 100% com o modelo.** Só para conferir o formato, o parser foi passado pelos arquivos reais (sem banco, sem imprimir conteúdo): 57 jogadores (40 ativos, 17 inativos), 231 partidas (27 com chuva), 6.337 presenças, 240 notas, 5 jogadores com lacuna, 12 diferenças esperadas (ajustes) e **1 rodada com valor simples e em dobro misturados, que gera 1 divergência** (um atleta com 3 numa rodada de chuva, onde o app daria 6). O script trata isso como divergência e **impede a execução real** até haver decisão (por exemplo, corrigir a origem ou definir como esse atleta entra). O dry-run em produção vai mostrar a mesma divergência.
2. `PATCH /jogadores/:id` usa o mesmo corpo do cadastro: sem `pontuacaoInicial` o padrão (0) sobrescreve o valor atual. A tela sempre envia o campo; cliente externo que omita o campo zera a inicial.
3. Etapa 1 no ar antes do script: o CHECK antigo de posição continua aceitando `defensor`/`meio_campo` até o deploy seguinte (contração, SDD §6).
4. A suíte da API leva ~25 min no Postgres local; duas execuções simultâneas colidem no banco `pelada_teste` (aconteceu uma vez aqui e gerou falhas falsas já descartadas).
