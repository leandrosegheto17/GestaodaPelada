## 1. Plano de execução
**Reaproveitamento:** USAR `ExecutorDb`/desembrulho de `infraestrutura/db/` (TP-0014); tabelas `pedidos_reset`, `auditoria`, `contas`, `grupos`, `vinculos_admin` em `tipos.ts` (TP-0025, TP-0026); `criarFabrica`, `relogioFixo` (TP-0017), `test/apoio/sql.ts` (TP-0025). Contas e grupos de teste: fábricas `test/apoio/fabricas/{contas,grupos,vinculos}.ts` dos TP-0027/TP-0029 se já existirem; senão via `test/apoio/sql.ts`, trocando para as fábricas antes de entregar (nunca fábricas duplicadas). Instante vem do chamador (`agora`, G-06).
**Camada:** `backend/api/src/infraestrutura/db/repositorios/{pedidos-reset.ts,auditoria.ts}` (módulo de dados); fábrica `backend/api/test/apoio/fabricas/pedidos-reset.ts`.
**Referência visual:** não se aplica.

1. `pedidos-reset.ts` (não é dado de grupo → "arquivo inteiro" em `backend/scripts/checagens/grupo-id-excecoes.json`):
   - `registrarOuAtualizar(db, contaId, agora)`: `INSERT … ON CONFLICT (conta_id) WHERE resolvido_em IS NULL DO UPDATE SET ultimo_pedido_em = EXCLUDED.ultimo_pedido_em` (inferência do índice parcial do TP-0025; atômico, sem corrida).
   - `listarPendentes(db)` → `[{ id, contaId, email, grupos: string[], ultimoPedidoEm }]` numa consulta (`array_agg` dos nomes dos grupos do admin via `vinculos_admin`, ordem alfabética; `coalesce` para `{}`), do mais recente para o mais antigo (ordem de `dono-painel.json`).
   - `resolverPorId(db, pedidoId, { resolvidoPor, agora })` e `resolverPorConta(db, contaId, { resolvidoPor, agora })` → boolean; só atuam em pendente (`resolvido_em IS NULL`); repetir é idempotente (false). `resolvidoPor` nulo = infraestrutura (script do dono).
2. `auditoria.ts`: `registrar(db, grupoId: string | null, { autor, acao, entidade, entidadeId, resumo, agora })` com `autor = { tipo: 'conta', contaId } | { tipo: 'infraestrutura' }` (casa com o CHECK do TP-0025). `grupoId` 1º (depois do executor) por convenção, `null` para ações sem grupo (dono, script). Só escrita: nenhuma leitura de auditoria nesta fase.
3. `resumo`: objeto pequeno (`Record<string, string | number | boolean | null>`), sem senha, token, telefone nem hash — a assinatura não aceita esses campos por nome (lista negada `senha*`, `token*`, `telefone`, `hash*` testada); o comentário da função diz que o resumo é para pessoas.
4. As duas funções aceitam `Tx` para entrar nas transações dos casos de uso (ADR-014 §3; ex.: TP-0037 resolve o pedido e audita junto).

Não fazer: rotas (TP-0039, TP-0059), redefinição de senha (TP-0037).

## 2. Plano de teste
`backend/api/test/repositorios/{pedidos-reset,auditoria}.test.ts` (pool de Workers + Postgres), dados de fábrica apagados em `afterEach` mesmo em falha, instantes de `relogioFixo` (t0 e t0 + 1 h):
- segundo pedido da mesma conta só atualiza `ultimo_pedido_em` (continua 1 linha pendente, mesmo id).
- `listarPendentes`: admin com 2 grupos → nomes em ordem; conta sem vínculo → `grupos: []`; dois pedidos em ordem do mais recente; uma consulta só (espião no executor).
- `resolverPorId` → some da lista; `resolverPorConta`; resolver de novo → false; novo pedido depois de resolvido cria outra linha pendente.
- auditoria com autor conta e com "infraestrutura" (`autor_conta_id` nulo); `grupoId` nulo e preenchido; `resumo` com chave `senha` ou `token` → recusado antes do banco.
- `registrar` dentro de `emTransacao` que lança → nada gravado.
Comando: `pnpm --filter @pelada/api test -- pedidos-reset auditoria` + `node backend/scripts/checagens/checar-grupo-id.mjs`.

## 3. Plano de validação de segurança
- RF-12/I-29/SDD §7: no máximo 1 pendente por conta, garantido pelo índice + upsert; pedido só referencia a conta (nada de IP/dispositivo, LGPD).
- RNF-12: auditoria só acrescenta (sem UPDATE/DELETE); autor obrigatório e coerente com o CHECK.
- G-08: `resumo` nunca carrega senha, token, hash ou telefone (teste de recusa por chave).
- `listarPendentes` é dado só do dono: o comentário aponta que só rota sob `/api/dono` (middleware do TP-0032) pode chamá-la; e-mail volta só aí.
