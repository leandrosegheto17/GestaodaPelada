## 1. Plano de execução
Achado (baixo, DevSecOps da RTP-0154): a base vem de `vars.CLOUDFLARE_API_BASE` (variável de repositório editável por quem tem permissão nas variáveis) e o script envia o token Bearer a ela sem validar esquema nem host; uma base alterada (host alheio ou http) exfiltra o token, e a aprovação do environment `producao` não mostra o valor da variável. Validar a base no script, depois do teste do token: exigir `https://`, host exato igual ao da Cloudflare (rejeitar `user@`, porta e host com sufixo parecido) e sem escrever o valor no erro. Sem URL literal no script (G-18): montar o host sem o esquema completo, ou validar no passo do workflow sem exceção nova. Os testes locais (http 127.0.0.1) precisam de um gancho que não exista no caminho de produção (ex.: o teste substitui o `curl` por um shim no PATH, em vez de afrouxar a validação).
**Reaproveitamento:** validação do token no mesmo script (RTP-0150); testes de `consultar-hyperdrive.test.mjs`.

## 6. Resultado do DevSecOps
Veredito: APROVADA. Revisão do diff + execução própria. Achados: 0 críticos, 0 não críticos.

LIDO (revisão do diff `consultar-hyperdrive.sh`, teste, DEPLOY.md):
- A validação roda depois do teste do token e antes de qualquer curl. Regex ancorada `^https://api\.cloudflare\.com(/[A-Za-z0-9._~/-]*)?$`, com esquema e host em variáveis internas do script (sem URL literal, G-18). Nada no ambiente a afrouxa: lê só `CLOUDFLARE_API_BASE`, o valor a validar.
- Token por stdin (`printf` é builtin, fora de argv; `--config -`), restrito a `[A-Za-z0-9_-]`. A mensagem de erro não ecoa o token nem a base. O curl não usa `-L`, então um redirect do host da Cloudflare não leva o token a outro host.
- `deploy.yml` e `checar-urls-absolutas.mjs` não foram tocados.

EXECUTADO (script real com stub de `curl` no PATH que registra as chamadas; token `tok_ABC-1`; 26 bases):
- rc 1, 0 chamadas, sem eco de token nem de "evil": `https://api.cloudflare.com@evil.com`, `...%2f@evil.com`, `...\@evil.com`, `...#@evil.com`, `...?x=@evil.com`, `https://api.cloudflare.com.` (ponto final), `apI` (maiúscula), homóglifo cirílico `і` em `apіi`, `https://[::1]`, `:443`, `\t`/`\r`/`\n` finais, `/\nevil` embutido, `/x\n`, `/%40evil`, `/a@b`, `/a b`, `http://`, `HTTPS://`, espaço inicial, `apixcloudflare.com`.
- rc 0 com curl chamado, sempre com host api.cloudflare.com: sem caminho, `/client/v4`, `/../x`, `//evil.com`. Esses são caminho, não host. O `@`, `?`, `#` e `\` só passam se vierem antes do primeiro `/`, e nesse caso a regex rejeita; depois do host o charset do caminho exclui `@ ? # \ % espaço`, então a semântica da URL não muda. `/../` e `//` podem alterar o recurso consultado dentro da Cloudflare, mas o token continua indo só à Cloudflare. Classificação: informativo, sem RTP (dentro do que o QA já observou).
- A URL final da chamada foi sempre `https://api.cloudflare.com<caminho>/accounts/<id>/hyperdrive/configs/<cfg>`. `CLOUDFLARE_ACCOUNT_ID` e `$1` não são validados, mas vêm depois do host fixo e não mudam o destino. Risco residual nulo para o token.
- Não reexecutei vitest, shellcheck nem actionlint: o QA já os executou e o diff não mudou.

Shim `curl` no PATH do runner: seria vetor só para quem controla o PATH ou os arquivos do runner. Esse atacante já lê o token do ambiente, então o shim não amplia o risco. O gancho existe só no teste, que injeta o shim no PATH do processo filho. O script de produção não tem toggle. Runner GitHub-hosted é efêmero e `deploy.yml` não instala nada no PATH. Sem achado.
