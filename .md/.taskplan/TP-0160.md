# TP-0160 — Migração de escalações

Reqs: SDD §5 (ESCALACAO); RF-48 · Aceite: escalacoes (grupo_id, data, formato, n, k, composicao `jsonb` validada pela aplicação, confirmada por/em; único por grupo e data)

## 1. Plano de execução
**Reaproveitamento:** USAR o runner `aplicarMigracoes` e a pasta `backend/api/src/infraestrutura/db/migracoes/` (TP-0015), `checar-migracao-aditiva.mjs` (TP-0016), o `globalSetup` de `backend/api/test/apoio/` (TP-0017), `backend/api/test/apoio/sql.ts` (SQL cru em teste, TP-0025), `TabelasBanco` em `infraestrutura/db/tipos.ts` (TP-0014) e as tabelas `grupos`/`contas` (TP-0026/TP-0025). Valores de `formato` iguais à tupla de `backend/contrato/src/enums.ts` (`dois_times|varios_times`, TP-0005); faixas de N e K da Seção 1.4 (`limites.ts`).
**Camada:** `backend/api/src/infraestrutura/db/migracoes/<AAAAMMDDHHMM>_escalacoes.sql` e `infraestrutura/db/tipos.ts` → módulo de dados (G-02); teste `backend/api/test/migracoes/escalacoes.test.ts`.
**Referência visual:** não se aplica.

1. Carimbo real do momento da implementação (posterior às migrações já existentes; SDD §6 evita colisão entre tarefas paralelas).
2. Tabela `escalacoes`: `id uuid PK default gen_random_uuid()`, `grupo_id uuid NOT NULL REFERENCES grupos`, `data date NOT NULL`, `formato text NOT NULL CHECK IN ('dois_times','varios_times')`, `n smallint NOT NULL CHECK (n BETWEEN 2 AND 11)`, `k smallint NULL CHECK (k BETWEEN 0 AND 20)`, `composicao jsonb NOT NULL CHECK (jsonb_typeof(composicao) = 'object')`, `confirmada_por uuid NOT NULL REFERENCES contas`, `confirmada_em timestamptz NOT NULL` (sem `now()`: vem do relógio, G-06).
3. `CONSTRAINT escalacoes_grupo_data UNIQUE (grupo_id, data)` — alvo do upsert do TP-0161 e índice da leitura por data (sem índice extra).
4. K ilimitado: `k NULL`. Regra `CHECK (formato = 'dois_times' OR k IS NULL)` (no formato 3+ não há K, P-27). Interpretação documentada no cabeçalho do SQL: em `dois_times`, `k NULL` = "ilimitado".
5. A forma interna de `composicao` (times, titulares, entram no 2º tempo, não entra) é validada pela aplicação com o schema de `contrato/simulador/escalacao.ts` (TP-0146); o banco só garante que é objeto. Sem FK para jogadores dentro do JSON (aceite).
6. Acrescentar `escalacoes` em `TabelasBanco` (reler `tipos.ts` antes: outras tarefas o editam).

Atenção: jogador excluído (RF-22) pode ficar referenciado no JSON de uma escalação antiga; quem lê (TP-0168) cruza com os ativos da data. Não fazer: repositório (TP-0161), gatilho de "substitui a anterior" (é o upsert), `ON DELETE CASCADE` de grupo (grupos não são apagados, ADR-016).

## 2. Plano de teste
`backend/api/test/migracoes/escalacoes.test.ts` (pool de Workers + Postgres; fábricas de grupo/conta do TP-0027/TP-0029; apaga o que cria no `afterEach` mesmo em falha; momentos do `relogioFixo`, datas derivadas, sem literal — CONVENCOES §7):
- inserção válida nos dois formatos; segunda linha na mesma (grupo, data) → `23505`; mesma data em outro grupo → aceita.
- `n` 1 e 12, `k` −1 e 21 → recusados; `k NULL` em `dois_times` aceito; `k` preenchido em `varios_times` → recusado; formato desconhecido → recusado.
- `composicao` = `'[]'`/`'1'`/`'"x"'` → recusada; `NULL` → recusada.
- `grupo_id`/`confirmada_por` inexistentes → violação de FK.
- `node backend/scripts/checagens/checar-migracao-aditiva.mjs` verde.
Comando: `pnpm --filter @pelada/api test -- migracoes/escalacoes` + a checagem.

## 3. Plano de validação de segurança
- G-03/ADR-005: `grupo_id NOT NULL` com FK em toda linha; unicidade por (grupo, data) nunca global.
- G-14: migração aditiva (só `CREATE`), uma transação; nenhum tipo proibido (G-07 não se aplica, sem valor monetário).
- LGPD: a composição guarda ids de jogador e flags, nada de apelido, telefone, nível ou idade no JSON (conferir no TP-0161/TP-0167; aqui só o tipo). Auditoria: `confirmada_por/em` (RNF-12).
