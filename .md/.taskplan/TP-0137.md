## 1. Plano de execução
**Reaproveitamento:** USAR e só referenciar (sem reescrever passos que já estão nos arquivos): `.github/workflows/deploy.yml` (TP-0135: nome `restauracao-<ambiente>-<run_id>` do branch, artefato `dump-predeploy-*`, instrução impressa na falha), `.github/workflows/backup.yml` e `.github/actions/dump-cifrado/` (TP-0136: formato custom + age), `backend/scripts/dono.ts` (TP-0041: `criar`/`redefinir-senha`, `--alvo producao`, confirmação do e-mail), `backend/scripts/migrar.ts` (TP-0015), schema de `contas`/`auditoria` (TP-0025) e o `crypt(…, gen_salt('bf', 12))` do repositório de contas (TP-0027). O que já estiver no `backend/README.md` (seções Deploy/Backup) vira link para o `DEPLOY.md`, não cópia.
**Camada:** `backend/DEPLOY.md` (documentação); `backend/scripts/ops/contar-linhas.sql` (consulta única de contagem por tabela, usada antes e depois de restaurar — evita repetir a consulta em dois lugares do runbook).
**Referência visual:** não se aplica.

1. `contar-linhas.sql`: para cada tabela de `public` (inclui `migracoes_aplicadas`), `SELECT '<tabela>', count(*)` gerado a partir de `information_schema.tables` (via `\gexec`), ordenado por nome; só leitura.
2. `DEPLOY.md`, seções curtas e com comandos exatos:
   - **Deploy:** produção = merge na `main` + aprovação no environment `producao`; homologação = disparo manual `teste`; o que cada passo faz (link para o `deploy.yml`).
   - **Volta atrás:** `wrangler rollback [--env teste]` (só o código) e, se a migração estragou dado, restaurar o branch `restauracao-*` pela API/console do Neon e trocar a origem do Hyperdrive (`wrangler hyperdrive update <id> --origin-…`, mantendo `--caching-disabled`).
   - **Restauração de backup:** baixar o artefato (`gh run download`), decifrar (`age -d -i <chave>`), criar branch novo no Neon, `pg_restore --no-owner --clean --if-exists` com `pg_restore` da versão do servidor, rodar `contar-linhas.sql` no antigo e no novo, trocar a origem do Hyperdrive para o branch novo; voltar atrás = apontar a origem de volta (SDD §6).
   - **Conta do dono:** `dono.ts criar`/`redefinir-senha` com `--alvo producao`; **SQL equivalente** para o console do Neon (transação: `INSERT`/`UPDATE contas` com `crypt($senha, gen_salt('bf', 12))`, `senha_temporaria = true`, `DELETE FROM sessoes` da conta, `INSERT INTO auditoria` com `autor_tipo = 'infraestrutura'`), com aviso de não colar a senha em lugar nenhum além do console e de trocá-la no 1º login.
   - **Checagem mensal (T-08):** conferir o último run verde do `backup.yml` (`gh run list --workflow backup.yml -L 1`), o workflow ativo, e revisar o painel de uso da Cloudflare/Neon (T-06); a cada 3 meses, repetir o ensaio de restauração (ADR-011 §3).
   - **Troca de domínio (ADR-010):** `ENDERECO_NOVO`, período de transição, Worker de 301 que preserva caminho e query, nova versão da TWA com `assetlinks.json` no host novo, `URL_PUBLICA` do environment.
   - **Anonimização sob pedido (LGPD, até a Fase 2):** `scripts/anonimizar-jogador.ts` com auditoria — se o script ainda não existir, o runbook diz "criar sob pedido" (SDD §6), sem inventar o comando.
3. Ensaio (resultado em `## 4`): antes, garantir dado fictício no branch `teste` (`dono.ts criar --alvo teste` e, pelo `pelada-teste`, um grupo com jogadores e uma partida), senão as contagens são todas zero e o ensaio não prova nada; depois, disparo manual do `deploy.yml` em `teste` (TP-0135) → baixar o `dump-predeploy-teste-*` → decifrar → restaurar num banco novo do Postgres local (`docker compose`, banco `pelada_restauracao`, trava de host local) → `contar-linhas.sql` no branch `teste` (só leitura) e no local, tabela das contagens lado a lado, iguais.
4. Não fazer: restaurar sobre `pelada` nem `pelada_teste` locais; usar dump de produção no ensaio; senha real ou chave no `DEPLOY.md`.

## 2. Plano de teste
- Ensaio acima é o teste do aceite: contagens iguais em todas as tabelas; `pg_restore` sem erro; comando e saída em `## 4`, apagando o banco `pelada_restauracao` e o arquivo decifrado ao fim.
- SQL do dono: rodar no Postgres local (banco descartável com as migrações) e conferir que a conta criada entra com a senha via `crypt` e fica com `senha_temporaria = true`; a auditoria passa no CHECK do TP-0025. Apagar o que criou.
- `contar-linhas.sql` com `psql -f` no banco local: uma linha por tabela, sem escrita.
- Revisão: cada comando do `DEPLOY.md` confere com os nomes reais dos workflows, artefatos, secrets e scripts (grep no repositório); `node backend/scripts/checagens/checar-ids-tarefa.mjs` e `checar-urls-absolutas.mjs` verdes.

## 3. Plano de validação de segurança
- G-21: nenhum segredo, string de conexão ou senha no `DEPLOY.md` nem no `## 4`; arquivo decifrado e banco de ensaio apagados ao fim.
- ADR-013/ADR-015: o SQL do console usa `crypt` com custo 12, marca a senha como temporária, encerra sessões e audita; dono só por script ou console, nunca pela interface.
- G-16: o ensaio escreve só no Postgres local; produção apenas leitura (`contar-linhas.sql`).
- LGPD: dump do `teste` só com dado fictício; nenhum dado real copiado para a máquina.
