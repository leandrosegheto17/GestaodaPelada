# TP-0018 — Snapshot e checagem de compatibilidade do contrato

Reserva: Livre
ID no TASK.md: TP-0018 · Lote: L04 · Agente: executor · Chapéu: Backend · Est: 0,75 d · Dep: TP-0005, TP-0003 · Status no TASK.md: Pendente
Reqs: ADR-009 (API compatível por um deploy); SDD §6 (service worker antigo); G-11, G-20 · Aceite: `pnpm --filter @pelada/contrato snapshot` exporta todos os schemas para JSON Schema em `backend/contrato/snapshot/`; `checar-compatibilidade` compara com o snapshot versionado e falha em campo de resposta removido ou renomeado, tipo trocado, enum com valor removido ou campo de entrada novo obrigatório, salvo entrada em `backend/contrato/QUEBRAS.md` com o plano de dois deploys; falha também se aparecer campo de entrada `eDono`. Passo no `ci.yml`. Matriz: campo movido para objeto aninhado, `optional` virando obrigatório, snapshot ausente (falha fechado)

## 1. Plano de execução
**Reaproveitamento:** usa `backend/contrato/src` de TP-0005 (schema de erro, enums, `limites.ts`, tipos primitivos) como primeiros schemas publicados, e o `.github/workflows/ci.yml` (job base) de TP-0003. Nada de código existe hoje (`backend/` ausente). Este é o mecanismo único que TP-0019 a TP-0024, TP-0145, TP-0146, TP-0180 e TP-0186 vão usar: eles só registram schemas, nunca reimplementam a comparação. Também substitui o `API-CONTRACT.yaml` (L-14: YAML só gerado do snapshot, nunca escrito).
**Camada:** `@pelada/contrato` (`backend/contrato`). Registro em `src/registro.ts`; ferramenta em `backend/contrato/ferramentas/` (fora de `src/`, que é só schema sem lógica, SDD §2); saída em `backend/contrato/snapshot/`.
**Referência visual:** não se aplica.

1. `src/registro.ts`: mapa `nome → { direcao: 'entrada' | 'resposta', schema }`. Cada módulo de contexto exporta o seu objeto `esquemas` e o registro só os junta (uma linha por contexto). Nesta tarefa entram os schemas de TP-0005 (erro = resposta).
2. Exportação: `z.toJSONSchema` nativo do zod 4 (`io: 'input'` para entrada, `'output'` para resposta), chaves ordenadas, um arquivo por schema (`snapshot/<nome>.json`): tarefas paralelas de contrato não editam o mesmo arquivo. Se o TP-0001 fixou zod 3, parar e registrar bloqueio (não adicionar `zod-to-json-schema` sem decisão).
3. `ferramentas/comparar.ts` (função pura, testável): recebe snapshot antigo, novo e as quebras aceitas; devolve a lista de quebras com `esquema` + caminho JSON. Regras: resposta — propriedade removida, obrigatória virando opcional, tipo trocado, valor de enum removido, schema removido; entrada — propriedade obrigatória nova (inclusive `optional` → obrigatória), tipo trocado, enum com valor removido. Campo novo opcional, schema novo e enum ampliado são aditivos (G-20). Recursão em `properties`, `items`, `anyOf`/`oneOf` (ramos casados pelo `const` do discriminador; sem discriminador, pelo índice). Mover campo para objeto aninhado = remoção no caminho antigo.
4. Regra fixa (sem exceção por QUEBRAS): qualquer propriedade de schema de **entrada**, em qualquer profundidade, cujo nome normalizado (minúsculas, sem `_`/`-`) seja `edono` → falha (G-11, ADR-013).
5. `backend/contrato/QUEBRAS.md`: cabeçalho explicando o uso e tabela `| esquema | caminho | mudança | deploy 1 | deploy 2 |`. Quebra só é aceita se a linha casa esquema + caminho e as duas colunas de deploy estão preenchidas; linha malformada → falha.
6. `ferramentas/snapshot.ts` e `ferramentas/checar-compatibilidade.ts` (CLI finas). `checar-compatibilidade` gera em memória e compara com `snapshot/` versionado; também falha se o snapshot está desatualizado em relação ao código (mudança aditiva não regravada). `snapshot` roda a mesma comparação antes de regravar e se recusa a sobrescrever com quebra não listada em `QUEBRAS.md` — assim regravar não "lava" uma quebra.
7. Scripts no `package.json` do contrato (`snapshot`, `checar-compatibilidade`), rodando TS pelo mesmo mecanismo que o TP-0001 fixou (sem nova dependência). Passo `pnpm --filter @pelada/contrato checar-compatibilidade` no job base do `ci.yml` (caminhos relativos ao pacote, CONVENCOES §6). Gerar e versionar o snapshot inicial.
8. TDD: escrever primeiro os testes de `comparar.ts` (seção 2), depois a implementação, depois as CLIs.

Não fazer: escrever YAML/OpenAPI à mão; ler `.git`; aceitar quebra por flag de linha de comando; lógica de negócio em `src/`.

## 2. Plano de teste
Vitest em `backend/contrato/ferramentas/*.test.ts` com pares de schemas zod pequenos (fixtures em memória, sem arquivos do disco salvo o teste de CLI em pasta temporária).
- Aceite, cada um falhando: campo de resposta removido; renomeado (= removido + novo); tipo `string` → `number`; enum de resposta e de entrada com valor removido; campo de entrada novo obrigatório; entrada `optional` → obrigatória; resposta obrigatória → opcional; schema de resposta removido.
- Matriz adversarial (CONVENCOES §9): campo movido para objeto aninhado; campo dentro de array de objetos; ramo de `discriminatedUnion` perdendo campo; `nullable` acrescentado em resposta; `eDono`, `e_dono`, `EDONO`, `e-dono` em entrada aninhada e dentro de array → falha mesmo com linha em QUEBRAS; `eDono` em **resposta** → permitido (o `GET eu` devolve `conta.eDono`); snapshot ausente, pasta vazia, JSON corrompido → falha (código ≠ 0); `QUEBRAS.md` com linha sem plano de deploy → falha; snapshot desatualizado com mudança aditiva → falha com mensagem "rode snapshot".
- Passa: campo opcional novo, schema novo, enum ampliado, quebra listada corretamente em QUEBRAS.
- `snapshot` recusa regravar com quebra não listada (teste da CLI em diretório temporário).
- Comandos: `pnpm --filter @pelada/contrato test`, `pnpm --filter @pelada/contrato snapshot`, `pnpm --filter @pelada/contrato checar-compatibilidade` (exit 0 no repositório), mais a lista da Seção 1.6.

## 3. Plano de validação de segurança
- G-11/ADR-013: a regra de `eDono` em entrada é a checagem mecânica de que nenhuma rota escreve o papel de dono; conferir que não há como desligá-la (sem flag, sem exceção em QUEBRAS) e que falha fechado.
- G-20: falha fechada em snapshot ausente/ilegível; nenhum `try/catch` que transforme erro de leitura em sucesso.
- Sem superfície de rede, sem segredo, sem dado pessoal; nenhuma dependência nova (zod 4 nativo). Conferir no diff que o passo entrou no job base do `ci.yml` e não com `continue-on-error`.
